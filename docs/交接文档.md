## 一、项目是什么

**本地优先的个人日记 + 笔记应用**。React 单页应用跑在浏览器，数据由同机常驻 Node 进程落盘到 `backend/data/`，**不联网、不上传、不受清缓存影响**。视觉上是一套完整的**「我的世界 2D 像素材质」主题**。

- 规模：约 5000 行（不含测试），frontend 43 个源文件 + backend 6 个，54+ 次提交
- **明确不做联网部署**（部署配置已删除，README 已声明）
- **明确不做手机端适配**（用户 2026-11-01 定调：「这个就是纯 web 端」）⇒ 只在桌面浏览器 + 鼠标键盘下工作；`AppShell` 里那套 `md:hidden` 底部导航属历史遗留，不投入维护；审阅清单里「叶子点击区小于 44px」这类触控问题按**不作废但不排期**处理
- 用户是**非专业开发者**，诉求是「双击就能用」

## 四、🎨 视觉主题系统（改 UI 前必读）

`frontend/src/index.css` 定义了一套完整的 **「我的世界 2D 像素材质」** 主题，浅色=明亮户外、深色=洞穴。这是全应用的视觉基调，**任何新 UI 都必须遵守**：

- **全局无圆角**：`--radius: 0rem`，且 Tailwind 的 `--radius-lg/md/sm/xl` 全部映射为 0 → `rounded-lg` 等类实际无效
- **材质工具类**（`@layer utilities`）：`mc-stone`（石头按钮）、`mc-plank`（木板）、`mc-sign`（木牌标题）、`mc-anvil`（铁砧金属弹窗）、`mc-dirt`（泥土底）、`pixel-shadow/-sm/-lg`（硬像素投影）、`pixel-press`（按下位移）
- **描边**：一律 `2px solid var(--mc-outline)`（浅色深棕 `#2a1d10`，深色浅棕 `#b08d5f`）
- **文字色**：材质底上写死 `text-[#2a1c0d]`（深棕）或 `#f4f4f4`（金属上白字）
- **阴影写法陷阱**：Tailwind 任意值里 `var(--mc-outline)` 括号必须严格配对。**历史上曾有 4 处多写一个 `)` 导致阴影类整体失效**（导航、弹窗、气泡）——已修复，新增类名时务必注意
- 编辑器排版（`.tiptap h1/p/ul/blockquote/code/img`）也在此文件定制
- 心情色板在 `lib/mood.ts`：8 种心情，每种带 emoji/label/**马卡龙色**（森林叶子按此着色）

## 六、后端 API 全表（实测核对）

| 方法 & 路径 | 行为 |
|---|---|
| `GET /api/entries?year=&month=` | 列日记，可按年/月过滤 |
| `GET /api/entries/dates` | **只回日期数组**（升序），森林页算「距上/下篇」用，不传正文 |
| `GET /api/entries/:date` | 按日期取一篇；**这一天还没写 ⇒ `200` + `null`**（不是 404，免得首屏探路在控制台报红）；不是日期的路径才 404 |
| `GET /api/entries/id/:id` | 按 id 取 |
| `PUT /api/entries` | 按 date upsert（一天一篇） |
| `DELETE /api/entries` | **只清日记条目**，不动素材（`clearEntries`） |
| `DELETE /api/entries/:key` | 删单篇日记；`:key` **既可以是条目 id（uuid），也可以是日期 `YYYY-MM-DD`**，两条都认（2026-11-01 修：以前只认 id，传日期会 200 但什么都没删）。**只删条目本身，不再连带删素材**（素材与同日笔记共享池子，见第八节第 15 条）。返回 `{ ok: true, deleted: boolean }`——删没删要说清楚 |
| `GET /api/notes?date=` | 列笔记（不带 date 返回全部） |
| `PUT /api/notes` | 有 id 更新，无 id 新建 |
| `DELETE /api/notes` / `DELETE /api/notes/:id` | 清空 / 删单篇 |
| `GET /api/files?entryId=` | 列附件元数据；**不带 entryId 返回全部** |
| `GET /api/files/:id` | 下载（`Content-Disposition`，中文文件名用 `filename*=UTF-8''`） |
| `POST /api/files` | base64 上传（fileId/entryId/ext/name/type/size/base64） |
| `DELETE /api/files` / `DELETE /api/files/:id` | 清空 / 删单个 |
| `GET /api/images?entryId=` / `:id` / `POST` / `DELETE` | 同附件模式；`:id` 直接回二进制。`POST` 要求 `imageId`/`base64`，`imageId` 与 `ext` 收字符集校验（`^[A-Za-z0-9_-]{1,80}$` / `^[A-Za-z0-9]{1,6}$`），不合格直接 400 |
| `DELETE /api/data` | **全量重置**（日记+笔记+图片+附件），供"还原备份" |
| `GET /api/export` | entries + notes + files manifest + **images manifest**（前端导出实际不走它） |
| `POST /api/import` | 按 entries/notes/files/images 逐条 upsert |
| 其余 | 404；异常统一 500 |

**注意**：`readBody()` 现在有**请求体上限**（默认 32MB，可用环境变量 `DIARY_MAX_BODY_BYTES` 覆盖），超限返回 **413** 并断开连接；JSON 解析失败返回 **400**（不再静默成 `{}`）。`putImage`/`putFile` 写二进制用的是普通 `fs.writeFile`，**不是原子写**（只有 JSON 走 `_writeJSON`）。

## 七、数据布局与素材生命周期

```
backend/data/
├─ diary.json        Entry[]：{ id, date, title, content(TipTap JSON), mood, tags, createdAt, updatedAt }
├─ notes.json        Note[] ：{ id, date, title, content, createdAt, updatedAt }（一天可多篇）
├─ images/<id>.<ext> + images/manifest.json   { id: { entryId, ext, type } }
└─ files/<id>.<ext>  + files/manifest.json    { id: { entryId, ext, name, type, size } }
```

- **`entryId` = 日期字符串 `YYYY-MM-DD`**：同一天的日记与笔记**共用**同一个素材池（删素材要看日期，不能只看某一篇）
- **移除即删**：`Editor.onUpdate` → `asset-sync.snapshotAssets` 前后 diff → `purgeRemovedAssets` 立即 `DELETE` 被移出正文的素材
- **撤销陷阱**：移除后 `Ctrl+Z` 会恢复卡片但文件已删 → 失效卡片（用户已明确接受此取舍）
- **孤儿素材兜底**：设置 → 维护 → 清理未引用素材（`cleanup.ts`，全库扫描比对引用）
- 导入备份用 `clearAll()`（= `DELETE /api/data`）全量重置后按原 id 还原

## 八、⚠️ 关键约定与坑位（34 条）

1. **改后端必须重启进程**；前端 Vite 会 HMR。用户常忘重启 → 新 API 404。
2. **`store._enqueue` 串行写队列内不能再调用会入队的公共方法**（死锁）。必须用 `_xxx` 无入队内部版本（现有 `_rmFilesByEntry` / `_clearAllFiles` / `_clearAllImages`）。
3. **JSON 写入是原子的**（`.tmp` + `rename`），且 Windows 下目标被读句柄占用会抛 `EPERM/EBUSY` → 必须走 `_renameOver` 退避重试，**别"简化"掉**。读侧同理：`_readFileWithRetry` 只对 `ENOENT` 回退成空，**`EPERM/EBUSY/EACCES` 必须退避重试后抛出，绝不回退成空数组** —— 曾经一律回退，并发写时读方会读到"瞬间变空"，上层当成日记全没了（`store.test.mjs` 的「原子写入：并发读永远不会读到"瞬间变空"」用例偶发失败抓的就是它）。
4. **React 19 StrictMode**：开发期每个 effect 挂载即跑两次。所有副作用（保存、fetch、删除）都要幂等。
5. **`setContent(value, false)` 不触发 onUpdate** —— "移除即删"机制成立的前提，**别改成 `true`**，否则切换日期会误删素材。
6. **`Editor` 的外部 value 同步靠 `JSON.stringify` 深比较**，大文档下有性能成本，别在 onChange 里塞大对象。
7. **Tailwind v4 任意值类名括号必须配对**（曾有 4 处多一个 `)` 导致阴影类失效）。写 `shadow-[...]`、`bg-[var(--x)]` 时务必核对。
8. **主题是硬约束**：全局 `--radius: 0`、2px 描边、硬像素投影。新增 UI 用现成 `mc-*` 工具类，别引入圆角/柔和阴影。
9. **后端默认 `127.0.0.1`**（`HOST` 可放开）。本机 `localhost` **优先解析 `::1`** → Vite 代理与 bat 后端探活写死 `127.0.0.1`；前端探活仍用 `localhost`（Vite 绑 `::1`）。
10. **dev server 的 `no-store` + `cacheDir: .vite-dev` 别动**，治浏览器 `ERR_CACHE_READ_FAILURE` 白屏的。
11. **curl 测本机必须 `--noproxy '*'`**，否则走代理 502，会误判服务挂了。
12. **改路由要同步改 `test/mockApi.ts`**，否则前端测试与真实行为脱节。
13. `AppShell` 的 `<main>` 默认限宽 `max-w-3xl`(768px)；**宽内容路由**（`/calendar`、`/forest`）在 `WIDE_ROUTES` 里，`xl`(≥1280px) 时放开到 `max-w-6xl`。新增宽内容页面时记得加进那个集合，否则桌面端会偏挤。
14. 提交信息用**中文 conventional commit**；Node 用托管路径 `C:\Users\quan\.workbuddy\binaries\node\versions\22.22.2-2\node.exe`。
15. **`deleteById` 只删条目、绝不动素材**（素材按日期归属、与同日笔记共享池子，连带删会误删笔记还在用的文件）。要回收无引用素材走前端「清理未引用素材」；全量重置走 `clearAllData`。
16. **`Store` 的读路径有内存缓存**（四份 JSON 各一份，`_cache`）。读命中返回 `structuredClone` 深拷贝，写成功后同步更新、写失败则失效。因此**不要让多个进程同时写同一个 `data` 目录**（缓存只认本实例的写入）；外部改过文件需调 `store.invalidateCache()`。
17. **首屏主题不再闪烁**：`frontend/index.html` 的 `<head>` 里有一段同步内联脚本，先读 `localStorage['diary-theme']` 挂 `.dark`。它的判定规则**必须与 `ThemeProvider.getInitialTheme` 保持一致**，改一处就要改另一处。
18. **森林页的间隔标牌要避开树干**：`MonthTree` 只在空档 ≥7 天时挂一块 `空N天` 小标牌，位置 `badgeY = groundY - 22`（**必须悬在草地上方**，画进泥土带会被深色纹理糊掉），且 `|x - trunkX| < 78` 时往一侧挪开（78 = 树根外沿 ≈±57 + 标牌半宽 22）。短空档只在地面压一段 2px 虚线，不挂牌子。
19. **森林页是「暗树 + 发光叶子」**，这是刻意的设定，不是没调亮：树冠三档色只差 2~3 个色阶（`CROWN_SHADE #0b0917` / `CROWN_BASE #0e0c1d` / `CROWN_LIT #121024`），**叶子是画面里唯一的光源**（数据在哪、光在哪）。所以：① 不要往树冠里加噪点/斑块，试过，缩放后是一块迷彩脏斑 ② 树冠**不加轮廓光**（试过 `crown.rim` 整圈浅紫，放大看就是「给树勾了个线」，剪影实感全毁） ③ 改配色前先照 `docs/reports/2026-09-18-项目现状分析.md` 头部那条，回参考图逐带取样，别凭感觉配 ④ 树冠明暗是**整块平涂三段**（`t < 0.16` 亮、贴地最后两行暗、其余中间档；`t = row/(rowsCount-1)`）。2026-11-01 试过按枝层分成 10 层横条纹，用户否掉，原话「不用加什么层次」；也试过让明暗线跟着枝条向两侧下垂 —— 满树弯弯曲曲的条纹，比直线更乱。**别再往树冠里加分层/条纹**，暗是设定。
20. **树冠是「一整棵实心锥形」，不是「一根根分开的松枝」**（用户明确要求："树其实可以做成一颗整体的,不用做那么多分支"）。当前 `CROWN_RX=188 / CROWN_RY=188`，做法：18 层左右两个椭圆团叠成实心剪影（`halfAt(t) = pow(min(1, t/0.965), 0.85)`）+ **每列挂齿**的参差底缘（`TRI=11` 三角波 + 每段哈希，逐列连着填，`HEM_PAD=3`）+ 尖顶单团；轮廓再按行哈希柔化（约每 3 行「长出一格 / 收回一格」，只动最外侧那一格，**不往内部撒点**）。侧团（左右甩出的小枝尖）因为 18 层下只制造小疙瘩，已整段删除。`crownClumps` 里记了 6 条已验证的死路（分开的枝、一层层枝盘、伞骨、底部收口大团、等间距幂函数、9 层台阶感），**改之前先看注释**。2026-11-01 之后轮廓抖动收紧到 `jL/jR ±0.06`、`wobble 0.022/0.012`、侧团 `0.05~0.10 rx`——用户要的是**规整**塔型，把随机度再加回去就会退回「一块边缘毛躁的剪影」。
21. **「脏」的技术定义 = 中间色太多**。这一轮把用户说的「画面有点脏」逐项拆掉：5 色标插值出的 65 条渐变天空带、2 个 radialGradient 柔光（树冠背后那层灰雾）、叶子 opacity 0.13/0.26 的半透明光晕、`buildGround` 的随机碎石、`buildCrown` 的 texture 噪点。**现在的铁律**：整幅画 20 个色以内、一律平涂硬边不透明、**不出现任何 opacity < 1 的图形**（唯一例外是 `dimmed` 时叶子 0.4）。
22. **天空靠「密排色阶」而不是「插值渐变」**：`SKY_STOPS` 是 20 级，每级只差 1~3 个色阶，分界线在肉眼阈值以下。**不要试图用棋盘格抖动做色阶过渡** —— 5px 方块铺出来的棋盘格在这个尺度上读作「点状虚线」，1 行、3 行密度梯度两种都试过，全是虚线，已弃用。
23. **`PIXEL` 从 10 改成了 5**（用户说「好粗糙」的直接原因是 10px 格在 1160 宽画布上太粗，占画宽 0.86%，而参考图原生像素块只占约 0.15%）。连带影响：**所有写成 `cell * N` 的尺寸都会跟着缩一半**，`buildGround` 里的亮边/底缘压暗都已改成绝对像素再量化。改 `PIXEL` 前先全文搜 `cell *`。
24. **地平线和草地必须起伏**：`buildGround` 的 `topAt(col)` 用低频正弦（周期 200px+）做出地平线起伏，`crestAt(col)` 做出近景坡地（周期 400px）。**量化时先把 sin 值乘成像素再除以 cell** —— 曾写成 `Math.round(w / cell) * cell * 4`（w 只有 ±1.5），除以 5 恒为 0，起伏被量化吃干净，画面上就是一条直线。
25. **空月木牌要放在树干左侧、并且扎进草地**：`x = max(24, trunkX - w - 60)`、`y = groundY - h + 20`（底边压在草地上）、立柱从牌底伸到 `groundY + 70`。**居中不行** —— 牌子正压在树干轴线上，深底不透明把树干截成上下两段，读起来像树被劈开了；**也不能太靠左**（试过 `trunkX - 306`，会盖住树冠左下角那片枝，把整棵树咬掉一块）。立柱只到 `groundY` 则看起来像浮在空中。
26. **叶子方块尺寸由 `tree-layout.ts` 统一算**（`layout.leafSize`，`MonthTree` 只读不自己算）：`n <= 1` 时 22；否则 `gap = min(横向间距, 纵向档距)`、`raw = clamp(gap * 0.8, 10, 22)`、取偶且不小于 10（下限 8→10 是 2026-11-01 改的：树冠变窄后 31 篇会掉到 8px，和夜空星点分不开）。**封顶从 34 降到 22 是用户两次反馈"光点太大"的直接结果**，常见 10~22。**更关键的是放置时必须留白**：`half = leafSize/2 + LEAF_RING(4)`，用 `footprintFits()` 查九点（四角 + 四边中点 + 中心）是否全在树冠内 —— 只查中心会让靠边的叶子四角探出轮廓，近黑树冠上被啃出一个个方口子（用户原话"这树怎么有缺块"的根因之一，实测 8 篇时 7/32 片出界）。整块塞不下就往树冠内侧挪（`x += dir*k*PIXEL`，k=1..12）。**「太挤就横向错开」是 2026-11-01 加的**（用户问「日记多起来光点会不会出问题」，随后贴截图「这里不是有点挤在一起了吗」）。判据：两片叶子连同光晕不压住，中心距（**切比雪夫** `max(|dx|,|dy|)`，方块是方的，别用欧氏）必须 ≥ `leafSize + 2*LEAF_RING` —— ⚠️ 第一版写成 `leafSize/2 + LEAF_RING`（那是**一片叶子自己的半宽**，等于把间距缩了一半），代码自认为不重叠、屏幕上照样糊成一颗，被用户一眼看破；`tree-layout.ts` 的 `need` 上方留了这条教训。做法：`scanSpot()` 在「本列所有 y + 左右各挪 1~10 格（≤50px）」的候选里挑，两档打分 —— 能满足 `need` 的优先、档内优先不挪（每格 −2）、档外比「离最近叶子多远 − 挪动代价」；放完再跑 **3 轮松弛**（每片叶子轮流「拿下来」，在其余都摆好的前提下重放，只在离最近叶子更远时接受）—— 贪心按日期顺序放时，月末那几片的好位置已被占，31 篇会剩 3~4 对相碰，松弛能解开。实测：改前 28/30/31 篇分别有 1/1/3 对相碰，改后全 **0 对**；稀疏月份基本不挪（8~25 篇 0~10px，30/31 篇最多 35px，画布宽 1160）。`tree-layout.test.ts` 有回归用例守着（8/12/16/20/25/28/30/31 篇逐对断言）。
27. **前景灌木（`buildBushes`）已整块删除**：那排贴底边的圆鼓包在 5px 尺度上读成「栅栏」，参考图的前景是干净的暗部。画面下缘靠 `buildGround` 的 `dirt` 压暗收口就够。
28. **叶子纵向位置必须用「最远点采样」**，不能取「第一个不碰撞的位置」。`tree-layout.ts` 里 `placed[]` 记已放叶子，每片叶子把本列所有候选 y 都试一遍，挑离最近已放叶子**最远**的那个。演进过程：① 纯哈希定 y → 31 篇时聚堆 ② 每列分档位（`usedSlots`）→ 铺满了但排成一条整齐斜线（x 是日期线性函数，y 又被限制在「该列实心段」里，塔形树冠靠边的列实心段短 → y 只能贴底 → y = f(x)）③ 挑「第一个不碰撞」→ 全挤在树冠中下部、下半截一串阶梯 ④ 最远点采样才铺得开。**另：档位/抖动必须用 `hash2` 强混合，不能用 `h % SLOTS`** —— `hashDate` 是 FNV-1a，日期只差末位字符时 `h_final = (h_prefix ^ c) * 16777619`，而 16777619 ≡ 4 (mod 5)，于是 `h % 5` 随字符线性变化，档位跟着日期走，屏幕上就是一串斜着排的方块。
29. **`crownColumnRange` 的 `crown.grid` 是二维数组**（`grid[row][col]`），不是一维铺平。曾写成 `grid[row * crown.cols + col]`，等于拿行号去索引二维数组，`top` 恒为 0、`bottom` 只到第 1 行，每列可用范围被算成「只有顶上两行」，叶子全挤到树冠上部并沿塔形轮廓排成一条弧。
30. **树冠侧面的小团必须钳制外缘**：`cx + side * min(wantOut, w * 1.02 - tipRx)`。不钳的话偏移能到 `1.04w`、半径再加 `0.14rx`，合起来 `1.17rx` 冲出轮廓，树冠两侧鼓出一排「小翅膀」。
31. **树冠底缘不能是一条平直线，也不能靠「撒小团」拼**：只靠 tier 循环时最下面一层是宽度 ~0.5rx 的扁椭圆，底边就是直线，树冠像坐在板子上。2026-11-01 改成**直接改格子**（`buildCrown` 里 `HEM_PAD = 3` 留出底部余量，然后逐列算 `cutRow` 再往下挂齿）：
    - `cutBase = round((cy + ry + cell*0.5 - originY)/cell)`，先清空 `cutBase+1` 以下（削掉椭圆的圆屁股）；
    - 逐列 `lift = 2 - round(5.5 * pow(|rel|, 1.35))`（`rel = (c-mid)/mid`，中间高两头低 ⇒ 浅 V），`cutRow = cutBase - lift - (hash2(c,127) < 0.45 ? 1 : 0)`；
    - 齿：`TRI = 11`、`amp = 2.2 + hash2(seg,131)*3.2`、`tri = pow(1 - |((c%TRI)+0.5)/TRI*2 - 1|, 0.85)`、`depth = round(amp*tri)`；**逐列**把 `cutRow..bottom` 补实、`bottom+1` 以下清空。
    - **必须逐列连着填**。走过四条弯路：① 13 丛垂枝断开成漂浮黑块（行内断口 21 处、最宽 11 格，用户原话「这树怎么有缺块」）② 23 丛均分后连成一条托盘 ③ 反解轮廓下沿忘了归一化（`halfAt` 返回像素、比较值 0~1）⇒ 二分永远走到 t=1，垂枝全落到底边 ④ 先全局削平再挂齿 ⇒ 树脚下一串漂黑块。
32. **叶子方块不能是硬邦邦的正方形，也不能靠半透明做光晕**：`LeafBlock` 现在是 4 层纯色 —— ① 抖动光晕（**以方块中心为圆心的圆环**，内圈 `(gi+gj)%2===0` 填 `shade(color,-0.42)`、外圈只留 `gi%2===0 && gj%2===0` 填 `shade(color,-0.66)`，**像素画里唯一正确的柔化手段是疏密，不是透明度**）② 主体纯色 ③ 四角各挖 `notch = round(size*0.22)` 的 `CROWN_BASE` 方块变八边形 ④ 灯芯 `shade(color,0.45)`。**曾经外面套一圈 `CROWN_SHADE` 深色框，那正是"像贴纸"的元凶，已删。** 光晕距离必须用**到中心的欧氏距离**：用 `max(dx,dy)`（到外框的切比雪夫距离）算出来是一圈**方点虚线框**，还是像贴纸描边；而且外沿不能超过 `LEAF_RING(4)`，否则会在树冠边缘的夜空上撒下暗色方点。
33. **`_renameOver` 与 `_readFileWithRetry` 的重试退避必须带随机抖动**：`delay = min(10*i, 120) + random()*15`（读侧 `min(5*i,60) + random()*10`，`attempts` 分别 20 / 12）。纯等差退避会和「读者循环」形成**同频共振**，永远撞在同一个占用窗口上 —— 症状是全量测试连跑 3 次挂 1 次，报 `EPERM rename ... -> diary.json`。加抖动后连跑 5 次全绿。**这不是掩盖问题**：rename 失败会让这次保存真的丢掉，宁可多等也不能丢数据。
34. **树干顶端必须「插进树冠」，不能从地面往上量长度**：`trunkTopY = crownCY + crownRY - crownRY * TRUNK_TOP_INSET`（`TRUNK_TOP_INSET = 0.4`）。原来写 `trunkTopY = groundY - TRUNK_VISIBLE_H`（从地面往上量 100px）算出 458，而树冠底边在 415 —— **中间空 43px，山脊从缝里露出来，屏幕上就是树冠和树干断成两截**（用户原话"树干这里还是有断层"）。根因是「树干长度」和「树冠位置」是两个独立常量，改任一个都会重新裂开；改成从树冠底边往上量后，怎么调树冠尺寸都不会露缝。`tree-layout.test.ts` 有回归用例守着（0/1/8/31 篇四种密度都要求重叠 >20px）。**树干柱身是一根直柱（宽度恒定、不收分），但底部保留三级台阶树根**。三天里被用户改了三次，最终口径是两句原话合起来：「树干这里改回去吧,直直的就行,不用做什么层次了,你这层次做的真僵硬,不如直接不衔接了」+「**这个树根保留**」⇒ **柱身直、树根台阶留着**。`buildTrunk` 的 `roots` 是三级台阶：`for b = 1..3`，`grow = 4 - b`，`{ x: left - grow*cell, y: bottom - b*cell, w: w + grow*2*cell, h: cell }` —— **b=1 是最低那一行、也最宽**（往下张开，不是往上张开；写反了就是「倒扣的托盘」），颜色统一 `TRUNK_SHADE`，画在柱身之前，柱子盖住中间只露两侧；再加一格不对称的左根须。**不要再做逐行收分**：这个尺度一格 5px，连续渐变只会读成一节节台阶。粗细改 `buildTrunk(..., halfWidth)`（`MonthTree` 传 26）。**树脚的接触阴影试过又删了**（3 条 DIRT 横带拼扁椭圆，读成「树干底下横着一块板」）。

35. **写接口要 fail-closed：缺字段就当场 400，不许「悄悄写个脏东西进去还回 200」**。2026-11-01 全功能冒烟时踩到两个洞 —— ① `POST /api/images` 少传 `imageId` 会往清单里写一条 `id: "undefined"` 的记录，响应还是 200（后果：导出/导入带着一条永远取不到的图，森林页和编辑器都不报错）② `DELETE /api/entries/:date` 把路径里的日期直接喂给 `store.deleteById(id)`，日期永远匹配不到 id，于是**删了等于没删、还回 `{ok:true}`**。现在：`index.mjs` 里 `requireAssetKey(value,label)` / `normalizeExt(value,fallback)` 统一卡 `imageId`/`fileId`/`ext` 的字符集（顺带把「id 拼进文件名」的穿越面收掉），`DELETE /api/entries/:key` 先 `readAll()` 找 `id === key || date === key`，命中才删，并回 `deleted` 让调用方分得清「删掉了」和「本来就没有」。**判据**：`backend/index.test.mjs` 里三条用例守着（缺 imageId 400 且清单不变、`../evil` 类 id 400、按日期/按 id 都删得掉 + 删不存在的 `deleted:false`）。

## 九、常用命令

```bash
cd /d/日记网页
./node_modules/.bin/tsc --noEmit -p frontend/tsconfig.json      # 类型检查
./node_modules/.bin/vitest run --config frontend/vite.config.ts  # 137 个测试（前端 + 后端）
./node_modules/.bin/vite build --config frontend/vite.config.ts  # 构建 → frontend/dist/
```
启动（**一个文件，两种模式**）：

- 双击 `start-diary.bat` —— **日常用这个**（fast 模式）。先用 `node scripts/build-if-stale.mjs` 判断要不要 build（比 mtime：源码没改动就跳过，约 0.06s；有改动才跑 vite build，约 3.2s），再用**一个**后端进程在 5189 同时提供 `dist` 静态页面与 `/api`（后端已内置静态托管 + SPA 回退）。一个黑窗口、一个进程。
- `start-diary.bat dev` —— **改代码时用**。vite dev（5188）+ 后端（5189），保留热更新；`dist` 不参与。

**红线：不要在仓库里新建 `.bat` / `.lnk` / `.exe` 这类可执行文件。** 本机给「agent 新建的文件」继承了一条受限 SID 的 ACL（`S-1-4-…`），Explorer 会把它判成 Internet 区域 ⇒ 每次双击都弹「无法验证发布者」。原 `start-diary.bat` 是 zone 0，所以只能**原地改写它**（新文件 `<10` 字节也算 Internet 区；`Unblock-File` / `Set-Acl` / `icacls` 都改不回来，已实测）。判据：`powershell -NoProfile -ExecutionPolicy Bypass -File scripts\zone-probe.ps1 start-diary.bat` → 期望 `zone 0`。

**不要在会话里长期挂着服务**——用户习惯自己双击运行。
