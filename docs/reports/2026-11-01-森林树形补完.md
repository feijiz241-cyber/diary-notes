## 一、开工前看到的四个缺陷

放大到 1:1 逐块看（`bsk_inspect screenshot` 2218x1257 → `PIL` 裁剪 3~5 倍 NEAREST → `read_image`）：

1. **树冠是一个矮胖的椭球**，`CROWN_RX 215 / CROWN_RY 145`，宽高比接近 1.5:1，读起来是「一坨」而不是一棵杉树。
2. **轮廓毛躁**：`jL/jR` 抖动 ±13%、`wobble` 0.05/0.028、侧团随机外扩 22%，边缘是碎齿。
3. **底缘是一条宽平的水平边**，只在中间挂了两丛垂枝，缩略图上像「树脚垫了一块板」。
4. **树干是一根等宽方柱**（三段台阶但几乎一样宽）+ 两块 2 格高的暗宽板当树根 ⇒ 放大是「电线杆踩在木台座上」。
   另有一处「算出来但没接线」：`buildGround` 返回的 `crestTop`（坡地上缘亮边）`MonthTree` 从来没渲染。

## 二、改了什么（最终状态）

### 1. 比例：变高变瘦
`tree-layout.ts`：`CROWN_RX 215 → 188`、`CROWN_RY 145 → 188`、`CROWN_CY 270 → 252`。
`trunkTopY` 由 `crownCY + crownRY - crownRY*TRUNK_TOP_INSET` 自动跟随，不用改（交接文档第 34 条）。

### 2. 树冠剪影：18 层两团 + 单片尖顶
`crownClumps`：`tiers 11 → 18`；轮廓 `halfAt(t) = clamp(pow(min(1, t/0.965), 0.85), 0.07, 1)`；
`wobble = sin(t*π*2.3+0.7)*0.014 + sin(t*π*4.1)*0.008`；每层左右两团 `{cx ± wl*0.32, rx: wl*0.68, ry: bandRy}`，
`bandRy = span/(tiers-1)*0.66`，`jL/jR` 用 `hash2(i,91/97)` 扰动 ±3%。
尖顶换成**单团**：`tipR = (span/(tiers-1))*0.62`，`{cx, cy: topY + tipR*0.25, rx: tipR*1.15, ry: tipR*1.05}`。
**侧团（左右甩出的小枝尖）整段删掉** —— 18 层 + 5px 格子下它只制造小疙瘩和缺口。

### 3. 底缘：逐列「挂齿」，不再用小团拼
走过四条弯路（注释里逐条记了）：13 丛断开漂浮 / 23 丛均分变托盘 / 反解轮廓下沿忘归一化落到地 / 齿宽 2~3 格又叠成桌面。
最终改成**直接改格子**，`HEM_PAD = 3` 给底部留余量：

```ts
const cutBase = Math.round((cy + ry + cell*0.5 - originY) / cell)
// 每列：中间高、两头低的浅 V，再叠三角波 + 每段哈希
const lift = 2 - Math.round(5.5 * Math.pow(Math.abs(rel), 1.35))
const cutRow = cutBase - lift - (hash2(c,127) < 0.45 ? 1 : 0)
const TRI = 11, seg = Math.floor(c/TRI), amp = 2.2 + hash2(seg,131)*3.2
const tri = Math.pow(1 - Math.abs((((c%TRI)+0.5)/TRI)*2 - 1), 0.85)
// 逐列把 cutRow..bottom 补实、bottom 以下清空（必须逐列连着填，先削平再挂齿会掉出漂浮黑块）
```

### 4. 边缘柔化（用户：「边缘再柔一点」）
轮廓上按行哈希「长出一格 / 收回一格」，约每 3 行一次，**只动最外侧那一格**：

```ts
for (let r = 0; r < cutBase - 2; r++) { /* 取最左/最右实心列 */
  if (hl < 0.34) grid[r][l-1] = true;  else if (hl > 0.86) grid[r][l] = false
  if (hr < 0.34) grid[r][rt+1] = true; else if (hr > 0.86) grid[r][rt] = false
}
```
**没有往树冠内部撒点** —— 内部噪点缩放后是迷彩脏斑（交接文档第 19 条）。

### 5. 树干：直柱 + 底部三级台阶树根

这条改了三轮才定，写清楚免得再走：

1. 原始版本：一根等宽方柱 + 两块 2 格高的暗宽板当树根 ⇒ 放大是「电线杆踩在木台座上」。
2. 用户第一轮：「树干向树根的衔接再做好一点,现在很突兀」⇒ 我改成**逐行一格高的收分**
   （`hw = round(fullHalf * (0.72 + 0.28*pow(t,1.6)) / cell)`）+ **三级喇叭口树根**。
3. 用户第二轮全否：「**树干这里改回去吧,直直的就行,不用做什么层次了,你这层次做的真僵硬,不如直接不衔接了**」
   ⇒ 收分与树根整段删除，变成一根光柱。
4. 用户第三轮又截图指着树根说：「**这个树根保留**」⇒ 现在：**柱身直、树根三级台阶留着**。

```ts
// 柱身：一段直柱，上下同宽（不收分）
const body = [{ x: left, y: top, w: right - left, h: bottom - top }]
// 树根：三级台阶，b=1 是最低那行、也最宽 ⇒ 往下张开
const STEPS = 3
for (let b = 1; b <= STEPS; b++) {
  const grow = STEPS + 1 - b                     // b=1 → 3 格，b=3 → 1 格
  roots.push({ x: left - grow*cell, y: bottom - b*cell, w: w + grow*2*cell, h: cell })
}
roots.push({ x: left - (STEPS+1)*cell, y: bottom - cell, w: cell, h: cell })  // 一格不对称左根须
```

`MonthTree` 的绘制顺序：`roots` 填 `TRUNK_SHADE` → `body` 填 `TRUNK_BASE` → `bark` 填 `BARK`
（柱子盖住台阶中间，只露两侧；`rootsShade` 字段保留但为空）。
粗细只由 `buildTrunk(trunkX, trunkTopY, groundY, 26)` 的 `halfWidth` 决定。

**两条硬教训**：
- **不要做连续收分**：一格 5px、树干可见高度 ~90px（十几格），任何渐变都读成一节节台阶。
- **台阶必须往下张开**：`grow` 写反（越往上越宽）就是「倒扣的托盘 / 树冠踩高跷」，实测过。

### 6. 顺手补上 `crestTop`
`MonthTree` 在 `grassMid` 之后、`dirt` 之前补 `<Rects rects={scenery.ground.crestTop} fill={GROUND_TOP} />`。
中景坡地的上缘亮边终于画出来了，画面下半部不再是一整块平涂。

### 7. 叶子边长下限
`tree-layout.ts`：`const raw = Math.max(10, Math.min(22, gap * 0.8))`（原下限 8/6）——
树冠变窄变高后叶子间距变小，8px 的叶子会和星点混在一起、也不好点。

## 六、追加（同日）：日记写满一个月时，叶子会不会糊在一起

用户先问：「日记多起来，这光点显示会不会出问题？」量完改了一版交上去，用户贴了一张局部截图反问：「**这里不是有点挤在一起了吗**」—— 确实还挤着，原因是我把判据算错了一半。

### 判据（这里踩过一次，别再踩）

两片叶子「连同光晕」不互相压住，中心距（**切比雪夫** `max(|dx|,|dy|)`，方块是方的）必须 ≥ `leafSize + 2 * LEAF_RING`：每片叶子从中心到光晕外沿是 `size/2 + 4`，两片加起来就是 `size + 8`。

第一版写成了 `leafSize/2 + LEAF_RING`（= 9），那是**一片叶子自己的半宽** —— 相当于把最小间距缩小了一半，于是代码认为「不重叠」，屏幕上两团晕照样糊成一颗。用户看到的正是这个。

### 改前（按正确判据重测）

| 当月篇数 | leafSize | 需要中心距 | 相碰对数 | 例子 |
|---|---|---|---|---|
| 16 | 14 | 22 | 0 | — |
| 20 | 12 | 20 | 0 | — |
| 25 | 10 | 18 | 0 | — |
| 28 | 10 | 18 | **1** | 1 日↔2 日 dx0 dy10 |
| 30 | 10 | 18 | **1** | 1 日↔2 日 dx0 dy10 |
| 31 | 10 | 18 | **3** | 26↔29 dx15 dy15、26↔31 dx10 dy0 等 |

另：单棵树永远 ≤31 片叶子（一天一篇，`upsertByDate` 保证），写十年也不会更挤；1~31 篇全部 `outside=0`（没有一片叶子探出树冠）。

### 改法（`frontend/src/lib/tree-layout.ts`）

1. `need = leafSize + LEAF_RING * 2`。
2. `scanSpot(baseX, h, others)`：候选 = 本列所有可落的 y **加上左右各挪 1~10 格**（≤50px）的可落点；两档打分 —— 能满足 `need` 的优先（1e6），档内**优先不挪**（每格 −2），档外比「离最近叶子多远 − 挪动代价」。稀疏月份因此几乎不动，保住「x 表示日期」的读法。
3. **放完再跑 3 轮松弛**：每片叶子轮流「从板上拿下来」，在其余叶子都摆好的前提下重新找位置，只在「离最近叶子更远」时接受（严格变好 → 结果确定，同输入两次结果一致）。

为什么光靠贪心不够：按日期顺序放，写到月末那几片时好位置已经被占了，31 篇会剩 3~4 对相碰 —— 而几何上完全放得下（31 片 × 18px 只占树冠一小块）。让每片叶子都有机会「看着全体重来一次」就解开了。

### 改后实测

| 当月篇数 | 相碰对数 | 最大横向挪动 |
|---|---|---|
| 1 / 2 / 4 / 8 / 14 / 16 / 20 / 24 / 25 | 0 | 0px |
| 10 | 0 | 5px |
| 28 | 0 | 10px |
| 30 / 31 | 0 | 30~35px |

同一输入跑两遍 `computeLayout`，`leaves` 完全一致（确定性没被松弛破坏）。

### 判据（可复跑）

`tree-layout.test.ts` →「一个月写满 31 篇时，不可能有两片叶子连同光晕压在一起」：对 8/12/16/20/25/28/30/31 篇逐对断言中心距 ≥ `leafSize + 8`。注意**必须用切比雪夫距离**，欧氏距离会把「斜对角刚好压住」漏掉。

### 视觉核对

临时实例（5199 端口 + 临时数据目录，与真实数据隔离）写满 30 天，headless Chrome 截图核对：光点之间都留得开，没有两颗糊成一颗。核对完临时实例和临时数据都已删除。
