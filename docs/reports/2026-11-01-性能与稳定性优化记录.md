# 2026-11-01 · 性能与稳定性优化记录

> 本轮范围：用户从上一轮审计清单里点名两项 —— **A 组「后端没起时的提示 + 导入安全」**、**B 组第 5 条「图片只取用到的那一张」**。
> 用户明确表示 **不做自动备份与回收站**（原话：「自动备份和回收站不用做，我自己删日记有分寸」），据此本轮未实现任何自动快照/回收站机制。

## 一、改了什么

### B5 · 图片按 id 单张取（编辑器）

**问题**：`frontend/src/components/ImageNode.tsx` 的 `ImageView` 每个节点都调 `getImagesByEntry(entryId)`，而那函数是「先查当天清单，再把当天每一张图整份下载」。一屏 N 张图 ⇒ **N×(1+N) 个请求、N² 次全尺寸下载**。

**改法**：

- `frontend/src/lib/db.ts` 新增 `getImage(id)`：对应后端已有的 `GET /api/images/:id`，只取一张；404 返回 `null` 不抛错。
- 新增模块级 `imageBlobCache`（`Map<string, Blob>`，上限 32 张，按插入顺序淘汰）。只缓存**字节**，不缓存 blob URL —— URL 仍由组件在卸载时 `revokeObjectURL`，不会悬挂。
- `putImage` 成功后把刚上传的字节写进缓存 ⇒ **插入后立刻渲染，零请求**。
- `deleteImage` 与 `clearAll` 会清缓存，避免删了还能画出来。
- `getImagesByEntry` 改为复用 `getImage`，导出备份/清理孤儿素材这类「确实要整天素材」的路径也顺带受益。
- `ImageView` 改成状态机：`loading / ready / gone / failed`。以前拿不到图就永远是一个灰色脉冲方块；现在分别显示「图片没有找到（可能已被清理）」和「图片加载失败：确认那个黑色命令行窗口还开着」。

### A1 · 加载失败不再永久停在「加载中…」

**问题**：`getByDate` / `getAllNotes` / `getMonth` / `getYear` / `searchAll` 一旦 reject（最常见原因就是**后端进程没起来**），页面永久显示「加载中…」，用户无法判断是慢、是坏、还是自己没等够。

**改法**：

- 新增 `frontend/src/lib/api-error.ts` 的 `describeError(err)`：把 `TypeError: Failed to fetch`、`API 5xx`、`API 413` 等翻译成一句人话（例如「没连上本地服务。请看一眼那个黑色命令行窗口还在不在；如果关掉了，重新双击 start-diary.bat，再刷新本页。」）。
- 新增 `frontend/src/components/LoadError.tsx`：带 `role="alert"` 的错误块 + 「重试」按钮。
- 新增 `frontend/src/components/ErrorBoundary.tsx`，并在 `frontend/src/main.tsx` 包住 `<App />`：任何一屏渲染抛错都给出「数据还在磁盘上，重新加载页面」而不是白屏。
- 逐页补 catch：`DayEditor`（加载 + 保存）、`NotesPage`（加载 + 自动保存 + 删除 + 新建）、`ForestPage`（当月、全部日记、搜索、点叶子）、`CalendarPage`、`SearchPage`、`SettingsPage`（导出/导入/清理/清空/迁移）。
- 保存失败不再伪装成成功：
  - `DayEditor` 保存失败显示「保存失败，稍后会自动重试」，**并把草稿放回 pending、5 秒后重试**，内容不会因一次写失败而丢；
  - `NotesPage` 单篇笔记保存失败显示「保存失败」，并把 dirty 放回去等下次输入再试；
  - 卸载时的那次 flush 没有界面可提示，退化为 `console.error`（已注明原因）。

### A2 · 导入先校验，再清空

**问题**：`importBundle` 原本是「先 `clearAll()` 清空本地，再逐条写」。备份文件本身有问题（手改坏、复制截断、版本不匹配）时，用户得到的后果是「原有数据没了 + 新的也没进来」。

**改法**（`frontend/src/lib/export.ts`）：

- 新增 `prepareImport(bundle)`：**只校验与解码，不碰磁盘**。逐项检查 `version`、`entries[].date` 是否为 `YYYY-MM-DD`、`notes/files` 是否为列表、每条 `id` 是否存在、每个 `dataUrl` 是否完整且能 `atob` 解出来。任一项不合格就抛出带定位的中文消息（如「第 2 张图片的内容不是完整的 dataURL」）。
- `importBundle` 改为两段式：`prepareImport` 通过后才 `clearAll()` 并写入。
- 写入阶段若仍失败，错误文案**如实说明**「原有数据已经被清空，请再选一次同一份备份文件重试」——不粉饰。
- `SettingsPage` 的导入提示改为显示具体原因，不再统一说「文件格式不正确」。

## 四、动手时的注意点（给下一次）

- 图片缓存在模块内存里，**改完 `putImage`/`deleteImage` 的语义要同步维护 `imageBlobCache`**，否则会出现「删了还能画出来」或「换了还是旧图」。
- `describeError` 依赖「`fetch` 抛 TypeError」判断「后端没起」。若将来给 db 层加统一的 `request()` 包装并抛自定义 `ApiError`，记得同时更新这里的判定。
- 导入校验是**白名单式**的：新增导出字段时，要同步在 `prepareImport` 里放行，否则老用户的新备份会被判成不合法。

## 五、第二轮（同日追加）：搜索防抖 + 日期清单接口

用户点名这两项先做。

### 搜索防抖（`SearchPage` / `ForestPage`）

**问题**：两个搜索框都是「每敲一个字符 ⇒ 立刻把全部日记 + 全部笔记重新下载并全程扫描」。敲五个字 = 扫五遍全库，而且先后响应没有次序保护，慢的那次可能盖掉新的结果。

**改法**：

- 新增 `frontend/src/lib/use-debounced.ts` 的 `useDebouncedValue(value, delay = 250)`：停下 250ms 才把值交出去。
- `frontend/src/pages/SearchPage.tsx`：输入只更新 `q`，真正的搜索交给 `debouncedQ` 的 effect；加 `seq` 请求序号，`then/catch` 里先比对序号，过期的响应直接丢弃；顺带加「正在翻日记…」的进行中文案。
- `frontend/src/pages/ForestPage.tsx`：树上高亮的搜索同样防抖（effect 里原有的 `active` 标记继续负责丢弃过期响应）。

### 日期清单接口（不再为了算间隔下载全部正文）

**问题**：森林页的「距上/下篇」只用到**日期**，却调 `getAll()` 把每一篇的正文都下载了一遍（`content` 是 TipTap JSON，一篇几 kB 到几十 kB）。

**改法**：

- `backend/index.mjs` 新增 `GET /api/entries/dates` → `['2026-07-02', '2026-08-20', ...]`（升序）。**必须放在 `GET /api/entries/:date` 之前**，否则会被当成「一篇日期叫 dates 的日记」而 404。
- `frontend/src/lib/db.ts` 新增 `getEntryDates()`。
- `frontend/src/pages/ForestPage.tsx` 改用 `getEntryDates()`，删掉 `allEntries`/`allSorted` 两层 memo；effect 依赖从 `[entries, reloadKey]` 收敛成 `[reloadKey]`（以前每切一次月都会重新拉一遍全部日记）。
- `frontend/src/test/mockApi.ts` 同步加了这条路由（同样放在 `:date` 之前），否则前端测试与真实后端行为不一致。

### 新增回归测试（本轮）

- `frontend/src/pages/SearchPage.test.tsx`（4 条）：连敲三个字只扫一遍全库（断言 `searchAll` 只被调用 1 次且参数是最后一次输入）；清空输入不触发搜索且立刻收起结果；**先发的请求后回来不会盖掉最新结果**；搜索失败给出「没连上本地服务」提示。

- `backend/index.test.mjs` 追加 2 条：`GET /api/entries/dates` 返回升序日期数组、不含正文；不会被 `:date` 路由吃掉。

## 六、第三轮（同日追加）：生产模式启动器（后端直接托管 dist）

**问题**：`start-diary.bat` 永远只起 `vite dev`，`frontend/dist/` 虽然存在却从没被访问过 —— 相当于每天用「边编译边跑」的方式打开一个不需要再改的程序：多一个进程、每次都要预编译、浏览器拿到的也是未压缩的一千多个模块。

**改法**（用户选了「加一个启动器，保留原来的」）：

1. `backend/index.mjs` 内置静态托管：
   - 默认目录 `frontend/dist/`，环境变量 `DIARY_DIST_DIR` 可指向别处，`DIARY_DIST_DIR=off` 彻底关闭（只跑 API 用）。
   - 只接管**非 `/api`** 的 `GET/HEAD`；`/api` 下不存在的路径仍回 JSON 404，避免前端把 HTML 当 JSON 解析。
   - 前端路由回退：路径**没有扩展名**（`/forest`、`/day/2026-09-18`）时回 `index.html`，刷新和直接输地址都不会 404；**带扩展名却找不到**的资源回 JSON 404，绝不回 HTML（否则浏览器会拿 HTML 去当 JS 解析）。
   - 目录穿越防护：`decodeURIComponent` 之后 `path.resolve`，结果必须仍在 `dist` 之内（`..%2f`、`%2e%2e%2f` 都在这一关被拦）。
   - 缓存头：`/assets/*`（文件名带内容哈希）给 `public, max-age=31536000, immutable`；`index.html` 给 `no-cache`。顺带补了 `Content-Length` 与 `HEAD` 支持。
   - 启动时打印一行，说清现在是「静态页面：<目录>」还是「没找到 index.html，只提供 /api」，不再让用户靠猜。
2. 新增 `start-diary-fast.bat`：PATH 前置 node 22 → `vite build`（失败则明确报错、不启动任何进程、提示可以退回 dev）→ 只清理 5189（**不动 5188**，可能正有一个 dev 会话在用）→ `start /b node backend/index.mjs` → 探测 `http://127.0.0.1:5189/` 最多 15 秒 → 打开浏览器 → `pause` 保窗。
3. `start-diary.bat` 原样保留（改代码时的热更新入口）。README 与交接文档都写明了「日常用 fast、改代码用 dev」。

**每次启动都重新 build**（实测 2.4s）：宁可多花两秒，也不要出现「改了代码但打开的是旧包」这种最难查的问题。build 失败时旧 `dist` 仍在盘上，dev 模式照常可用。

**新增测试**：`backend/static.test.mjs`（8 条）—— `/` 返回 html 且 `no-cache`；`/assets/*.js` 返回 `immutable`；`/forest`、`/day/2026-09-18`、`/notes`、`/calendar` 全部回 index.html；缺失的 `.js` 回 JSON 404；`/api/nope` 仍是 JSON 404；三种目录穿越写法都读不到 dist 外的文件；`HEAD` 只回头不回体；`distDir: null` 时只提供 API 且不崩。

**实测（真起了一个后端，`DIARY_DIST_DIR` 指向真实 `frontend/dist`，端口 5199，临时数据目录）**：

```
/ -> 200 text/html          /forest -> 200 text/html      /day/2026-09-18 -> 200 text/html
/notes -> 200 text/html     /calendar -> 200 text/html    /settings -> 200 text/html
/assets/index-BqTJA-Wy.js -> 200 text/javascript, Cache-Control: public, max-age=31536000, immutable
/assets/nope-XXXX.js -> 404 application/json
/api/nope -> {"error":"not found"} 404 application/json   /api/entries -> 200
/ -> Cache-Control: no-cache
```

**验证**：`tsc` 0 错；`vitest run` **27 文件 / 189 用例全绿**；`vite build` 通过。

> 说明：`start-diary-fast.bat` 里的每条命令（build、清理端口、起进程、探测、打开浏览器）都单独实跑过，但整份 bat **没有双击执行**（会打开浏览器窗口，属于用户桌面上的可见副作用），首次使用请由用户自己双击确认。

**注意点**：

- 日常模式（5189）看到的是**上一次 build 的内容**；改了代码要么重新双击 `start-diary-fast.bat`（会自动 build），要么用 `start-diary.bat` 在 5188 上看实时的。
- 两个脚本可以同时存在（不同端口），但两个窗口关的时候要都关，否则下次启动会占用端口 —— 脚本里的 `taskkill` 已经会处理 5189，5188 由 dev 脚本自己清理。

## 七、第四轮（同日追加）：启动器不再每次都 build

**起因**：第三轮的 fast 启动器「每次启动都 build」虽然保险，但用户实际感受是「新入口也不快」—— 每天开机白等 3 秒多只为确认一行代码都没改。

**实测数据（本机，Node 22，`workspace` 目录，冷 build）**：

| 环节 | 耗时 |
|---|---|
| `vite build`（无改动也要跑满） | **3.19 s**（vite 自报 2.72 s + 进程启动） |
| 起后端到第一次 200 响应 | 0.28 s |
| `wait-for-server` 等到响应 | 0.14 s |
| 旧 bat 的探测循环（`timeout /t 1` 整秒 + 每次一个新 node 进程） | 0～1 s 白等 |
| 首屏字节合计（html + react + tiptap + index js + css） | **754 kB**（未压缩；gzip 后 235 kB） |

⇒ 改动前「双击到页面出现」≈ 3.2 + 0.3 + (0～1) + 浏览器启动 ≈ **4.5～5.5 s**，其中 3.2 s 是纯粹白等。

**改法**：

1. 新增 `scripts/build-if-stale.mjs`：比对「输入文件里最新的 mtime」与「`dist/index.html` 与 `dist/assets` 中较早的那个 mtime」。
   - 输入 = `frontend/src` 递归 + `frontend/index.html` + `vite.config.ts` + `tsconfig.json` + `package.json` + `package-lock.json`。
   - 源码更新 ⇒ 构建；没更新 ⇒ 打印「源码没有改动，直接用上次构建的结果（N 分钟前构建），跳过构建。」并 **0.06 s 退出**。
   - **判据保守**：dist 缺文件、读 mtime 抛错，一律当作「需要构建」，绝不因为判断不了就跳过（否则会出现「改了代码打开旧包」这种最难查的问题）。
2. 新增 `scripts/wait-for-server.mjs`：一个进程内 100 ms 轮询，最多 15 s，成功 exit 0、超时 exit 1 并打印最后一次错误（如 `ECONNREFUSED`）。替掉 bat 里「每次都新起一个 node + `timeout /t 1`」的循环，去掉整秒粒度带来的白等。
3. `start-diary-fast.bat` 改成 `[1/3] node scriptsuild-if-stale.mjs` → `[2/3] 起后端` → `[3/3] node scripts\wait-for-server.mjs ... 15000`，失败分支改成 `goto server_unreachable`（不再依赖块内 errorlevel 展开）。**（`start-diary-fast.bat` 后来在第八节里被删掉了：fast 模式并回了 `start-diary.bat`。）**

**实测（同一台机器，改完）**：

- 源码没改：`build-if-stale` **65 ms**（`real 0m0.065s`，含 node 启动）→ 起后端 0.28 s → 等到响应 0.14 s ⇒ **双击到浏览器打开约 0.5 s**（不含浏览器自身启动）。
- 碰一下 `frontend/src/index.css` 再跑：正确识别「比上次构建新约 N 秒」并重新构建 3.19 s，产物哈希与内容不变。
- 再跑一次：正确跳过。
- `wait-for-server` 两个分支都验过：端口上什么都没有 ⇒ 800 ms 后 exit 1 并打印「在 800ms 内没有响应（最后一次：ECONNREFUSED）」；真起服务 ⇒ 140 ms 后 exit 0。

**刻意没做**：

- **没有给静态资源加 gzip**：本机回环传输 754 kB 只花几毫秒，真正的成本是浏览器解析那 700 kB JS，压缩不减少解析时间。等以后真要从外网访问（当前明确不做）再考虑。
- **没有按路由拆包**：落地页就是今日日记 = 编辑器，tiptap 无论如何都在首屏关键路径上，拆了也省不掉。真要减，只能换编辑器或砍插件，属于产品决策不是优化。
- 脚本本身没有写成 vitest 用例（它操作的是仓库自己的 `dist`，跑测试时构建等于污染工作区）；改为上面那组手工可复跑判据。

## 八、第五轮（同日追加）：双击不再弹安全警告 + 启动器合并成一个

**起因**：用户双击 `start-diary-fast.bat`（以及后来那个 `启动日记.lnk`）时，Windows 每次弹「打开文件 - 安全警告 / 无法验证发布者 / 来自 Internet 的文件」。用户的原话是「每次都弹」「老的不会触发告警」——即**老的 `start-diary.bat` 双击不弹**。

**真因（已定位，不是内容问题、不是来源问题、也不是 SmartScreen）**：

Windows 判断一个文件「来自 Internet」靠的是 `IZoneIdentifier`，而这个 zone 值**没有**存成 `Zone.Identifier` 备用数据流（实测 `Get-Item -Stream *` 只有 `:$DATA`，`Unblock-File` 前后完全一致）。真正的差异在 ACL 上：

| 文件 | zone | ACL 差异 |
|---|---|---|
| `start-diary.bat`（仓库原有） | **0（本地）** | 4 条标准 ACE，`AreAccessRulesProtected=False` |
| `start-diary-fast.bat`（agent 新建） | **3（Internet）** | 多一条 `S-1-4-102029406-819591806 Allow DeleteSubdirectoriesAndFiles, Write, Delete, Synchronize`（继承自工作区目录，沙箱给新文件加的受限 SID） |
| `启动日记.lnk`（agent 新建） | **3** | 同上 |

判据脚本：`scripts/zone-probe.ps1`（PS7 里没有 `System.Security.Policy.Zone`，所以走 `powershell -NoProfile -ExecutionPolicy Bypass -File`）：

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/zone-probe.ps1 start-diary.bat README.md
# start-diary.bat -> zone 0
# README.md -> zone 3
```

**决定性实验**（证明「新建」这件事本身才是原因，与内容无关）：

- 把 zone 0 的 `start-diary.bat` 分别用 `cp`、PowerShell `Copy-Item`、`node fs.copyFileSync` 复制成新文件 ⇒ **三个副本全部变成 zone 3**。
- 新建一个 20 字节、内容无关的 `.bat` ⇒ zone 3。
- 反过来：用 `python` 以写模式**原地重写** `start-diary.bat`（同一个 inode、ACL 不变）⇒ 仍然是 **zone 0**。

⇒ 结论：**在本机这个工作区里，只要是新建的可执行类文件就带 Internet 区标记，且没有可靠的程序化办法改回 0**（`Unblock-File` 无 ADS 可解；`Set-Acl` 把老文件 4 条 ACE 覆盖上去后 zone 仍为 3；`icacls /inheritance:e` 反而把受限 SID 继承回来）。唯一出路是**不要在仓库里新增可执行文件，改成原地改写老文件**。

**改法**：

1. **删掉** `start-diary-fast.bat` 和 `启动日记.lnk`（`rm -f`），把 fast 模式并进 `start-diary.bat`。
2. `start-diary.bat` 现在长这样（**行尾必须是 CRLF，见下**）：
   - `if /i "%~1"=="dev" goto dev_mode` —— 不带参数 = fast（日常），带 `dev` = 老的开发模式。
   - fast：`[1/3] build-if-stale` → `[2/3]` 只清 5189（**不动 5188**）并 `start /b node backend/index.mjs` → `[3/3] wait-for-server 15000` → 开浏览器 → 打印「running at http://127.0.0.1:5189 (single process, fast mode)」→ `pause`。
   - dev：逻辑与原版一致（清 5188+5189 → 起后端与 vite dev → 分别探测 → 开 5188 → pause）。
   - 新增 `set SLEEP=%SystemRoot%\System32\timeout.exe`：从 bash 里跑 bat 时，`timeout` 会先命中 Git 自带的 GNU `timeout.exe`，报 `timeout: invalid time interval '/t'`；写全路径后两种环境都对。
   - 新增两个只给自动化测试用的开关：`DIARY_NO_BROWSER=1`（不弹浏览器）、`DIARY_HEADLESS=1`（不 pause）。
   - 头注释里写了「为什么只有一个文件」，避免下一个人再建第二个 bat。

**第二个坑（CRLF）**：第一版沿用老文件的 LF 行尾（Python `newline='\n'`），结果 dev 模式跑到 `goto wait_frontend` 时报「系统找不到指定的批处理标签 - wait_frontend」——cmd 在纯 LF 的大文件上 `goto` 标签查找会失效。改成 **CRLF**（`newline='\r\n'`，`od -c` 里能看到 `\r \n`）后正常。**注意：原地改写不会改变 zone，所以可以安全地改行尾。**

**实测（headless 真跑，可复跑）**：

```bash
# fast
DIARY_HEADLESS=1 DIARY_NO_BROWSER=1 cmd //c start-diary.bat      # 期望 exit=0
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:5189/  # 期望 200

# dev
DIARY_HEADLESS=1 DIARY_NO_BROWSER=1 cmd //c start-diary.bat dev  # 期望 exit=0
# 期望 5188 -> 200 且 5189 -> 200
```

结果：fast 输出 `[build] 源码没有改动…跳过构建` + `[diary-server] listening on http://127.0.0.1:5189` + `静态页面：D:\日记网页\frontend\dist\`，exit 0，`/` 返回 200 与真实 HTML；dev 输出 `VITE v6.4.3 ready in 296 ms`，exit 0，5188/5189 都 200。测完已 taskkill 清掉两个端口。

**注意点**：

- dev 模式 stderr 里偶尔会冒出几行 taskkill 的「无法终止…」提示（`>nul 2>&1` 没吃掉子进程的输出），不影响退出码和启动，目前不作处理。
- **`.bat` 本身仍没有被双击执行过**（那会在用户桌面上弹出浏览器窗口，属于可见副作用）；验证方式是 headless 跑同一条命令链 + curl 探端口。第一次由用户双击时才是终极验证。

## 九、第六轮（同日追加）：首屏那个红色 404 不再是「错误」

**起因**：用户截图问「这是什么错误？」—— 打开首页时 `GET /api/entries/2026-11-01` 在控制台里是一行**红色 404 (Not Found)**。

**它本来就不是错误**：`DayEditor` 打开时会按日期探一次，这一天还没写，后端按 REST 惯例回 404，前端 `getByDate` 里 `if (res.status === 404) return undefined` 早就把它当成「空日记」，页面正常显示空白编辑器。功能一直是对的，**红字只是浏览器的观感问题**。

**但观感问题也是问题**（用户会反复看这个界面，每次开机先看到一行红字），所以改掉：

1. `backend/index.mjs`：`GET /api/entries/:date` 分两种情况——
   - 路径**像日期**（`/^\d{4}-\d{2}-\d{2}$/`）：回 `200` + `null`（这一天没写）或 `200` + 条目。
   - 路径**不像日期**（`/api/entries/hello`）：仍然 `404 {"error":"not found"}` —— 不能把拼错的 URL 也当成「空日记」，否则真写错前端路由时会静默变成空页面。
2. `frontend/src/lib/db.ts` 的 `getByDate`：`404` 与 `null` 都归一成 `undefined`（**旧后端也照样能用**，不需要前后端同时升级）。
3. `frontend/src/test/mockApi.ts` 同步成 `ok(e ?? null)`，保持测试环境与后端一致。
4. 测试：`backend/index.test.mjs` 新增 2 条（日期不存在 ⇒ 200 + null；非日期路径 ⇒ 404），原「删掉日记后再取应是 404」的断言改成 200 + null；`frontend/src/lib/db.test.ts` 新增 1 条（还没写的一天返回 `undefined` 而不抛错）。

**验证（可复跑）**：

```bash
node ./node_modules/typescript/bin/tsc --noEmit -p frontend/tsconfig.json   # exit 0
node ./node_modules/vitest/vitest.mjs run --config frontend/vite.config.ts  # 27 文件 / 192 用例全绿
node ./node_modules/vite/bin/vite.js build --config frontend/vite.config.ts # index-BU0C19jr.js 369.94 kB
```

真起后端冒烟（临时 `DATA_DIR`，端口 5197）：`/api/entries/2031-02-03` → **200 `null`**；`/api/entries/not-a-date` → **404 `{"error":"not found"}`**；`/api/entries/dates` → `200 []`。

**注意点**：接口语义变了（404 → 200/null），这是**有意的不兼容改动**。当前只有一个前端在用它，且前端已同时兼容两种返回；如果以后有外部脚本靠 404 判断「这篇不存在」，要改成判断 `null`。
